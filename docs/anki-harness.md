# 漫画 Anki 筛选与制卡 Harness

核对日期：2026-09-29。入口为漫画“分词 → Anki 制卡”；候选仍保存在每书 `study-list.json`，本功能将确定性筛选、可选 LLM 筛选、制卡草稿、人工审核与 `.apkg` 导出接起来。

## 参考项目：`manga_anki` 的实际做法

已阅读本机 `/Users/heyanle/Desktop/project/manga_anki/factory/skills/manga-anki/scripts/{analyze,export,filter_deck,images}.py` 及项目文档。它以每部漫画为项目，OCR 后由 Sudachi B 粒度分词，结合作品内频次、通用词频、人工词汇规则与 JLPT 参考筛选；中文释义和截图经过单独审核。`genanki` 把稳定 GUID、固定 note type、原句高亮、审核裁图写入 `.apkg`，再检查 SQLite、媒体与输出哈希。重建失败不会覆盖上一份牌组，历史版本保留。

本应用已有 Kuromoji、JLPT 候选、词典、翻译配置和 LLM 配置，因此没有把项目私有 OCR 模型、Sudachi 或 Python 环境复制进应用。借鉴的是：**词语与原文出处分开保存、筛选与审核分开、固定笔记身份、只用原图真实文字框裁图、导出前检验**。参考项目本身也未完成 Anki 客户端实际导入验收；不能把它的 232 张卡视作本应用的质量指标。

## 页面流程

1. **规则筛词**：左侧按“学哪些等级、排除哪些明显无用词、只保留重复词、参考通用词频”改规则，右侧立即预览“候选 → 预计保留/排除”及逐词原因；点击应用才修改正式词单。N5–N1 独立复选，默认 N3/N2/N1；未收录和等级冲突可以分别选择，旧书的合并设置仍兼容。新增词性、专名、数词、分词器未知词、每书排除词、次数和词频规则默认关闭。“精简候选”只填入核心词性、专名/数词排除和至少出现两次，仍需应用；Zipf 仍由用户单独启用。JLPT 只是社区参考，不代表用户真的掌握某级词。
2. **AI 语境筛选（可跳过）**：从已应用的规则结果开始，选择 LLM 配置和 F1/F2/F3。每批返回 ID、决策和一句理由，页面显示进度、临时保留/排除/待审、请求数和粗略剩余时间；**全部完成前不改正式选择**。格式错时自动拆半；中断后可续跑，也可明确选择“只使用已完成判断”：已判 `keep/review` 入选，已判 `reject` 和未处理项暂不制卡，检查点保留。已有检查点时，人工改词和重新生成候选需先续跑或明确放弃，避免输入变动使续跑失效。
3. **确认词单**：优先显示 AI 待审词；候选详情先显示原句、筛选原因，再统一提供“按已应用筛选结果 / 手动保留 / 手动排除”。手动保留跳过后续自动筛选，明确排除优先。完整 AI 筛选的待审词须人工处理后才进入制卡；只使用已完成判断的快捷路径允许先制卡，仍标出未人工处理的待审风险。
4. **制卡与导出**：选择 R0–R3 和翻译配置；R1–R3 还选 LLM 配置，且可与筛选使用不同配置。R0 每卡保存，R1–R3 每批保存；格式错时拆半重试，已完成批次可续跑。R3 复核有争议的卡需人工确认。导出时从原始漫画页的 OCR 文字框裁 PNG，打入 `.apkg`；若候选/选择或 OCR 块文字已变化、裁图失败或缺出处，拒绝导出旧草稿。旧 TSV 路线继续保留。详细交互见[筛选 UX](anki-filter-ux.md)。

## 档位与选择依据

| 档位 | 做什么 | 额外 LLM 调用 | 适合 |
|---|---|---:|---|
| F1 快速排噪 | 每批 12 词，剔除明显乱码、纯专名或无意义片段；存疑保留 | `ceil(候选/12)` | 候选多、只想先去噪 |
| F2 语境筛选 | 每批 8 词，逐项检查词形、读音、原句和 OCR 疑点 | `ceil(候选/8)` | 更重视语境，能接受更多输出 |
| F3 双轮复核 | 每批 8 词，筛选后再请求复核；意见冲突变待审 | `2×ceil(候选/8)` | 错删代价高，愿意人工处理分歧 |
| R0 翻译卡 | 翻译目标词和原句，附原文框裁图 | 0；每词最多 2 次翻译 | 最快、无 LLM 配置 |
| R1 语境词义 | 每批 6 卡，在 R0 基础上生成本句词义 | `ceil(卡数/6)` | 需要中文语境解释 |
| R2 学习提示 | 每批 6 卡，加一条有价值的变形/搭配/语气提示 | `ceil(卡数/6)` | 想看简短用法 |
| R3 生成＋复核 | 每批 6 卡，生成后独立请求复核；存疑卡进人工审核 | `2×ceil(卡数/6)` | 重视卡片可信度 |

以 200 词/卡为例，正常调用数从旧的 F2 200、F3 400、R1/R2 200、R3 400 降到 **25、50、34、68**。若模型输出漏 ID、重复 ID、非法 JSON 或报告上下文超限，仅拆分出错批次，实际调用会增加；单项仍不合格时停下供用户换模型或修正。鉴权和普通网络错误不会盲目拆批。批处理减少请求往返和重复指令，但原句和每张卡的内容仍要传输，不能按请求数等比例推断 token 费用下降。
这里的“批处理”是在**一次普通 Chat Completions 请求里放多项**，可继续使用现有 OpenAI 兼容配置。它不是某家供应商专用的异步 Batch API；例如 [OpenAI Batch API](https://platform.openai.com/docs/api-reference/batch/object) 要上传 JSONL 并按最长 24 小时的窗口异步执行，不适合作为本地即时交互的唯一实现。

筛选、制卡和复核共用一个提交函数 `submit_anki_harness_result`，按阶段切换严格 JSON 参数 schema；请求强制选择这个函数并关闭并行工具调用。函数参数就是本轮结构化答案，不需要再给模型发送一条 `tool` 回执。应用仍校验每个候选 ID、数量和字段后才持久化；端点明确拒绝工具参数时仅回退一次纯 JSON，同一配置在本次运行中记住兼容性。F1–F3、R1–R3 每本书可选 1/2/3 个在途批次，默认 2；全应用 LLM HTTP 在途上限 4。R0 仍顺序翻译，避免一次把翻译端点推满。并发批次独立落盘，失败时中止新批次并等待已在途工作结束；成功后卡片恢复原候选顺序。并发只可能减少等待时间，真实加速和限流表现需按所选服务实测。[OpenAI 官方函数调用文档](https://developers.openai.com/api/docs/guides/function-calling)给出了 `tools`、强制 `tool_choice` 与函数参数返回的协议。
批量大小参考了本机 `manga_anki` 已导出的 232 张卡：已审核例句长度中位数 10 字、95 分位 21 字、最长 37 字。这只说明该样本适合小批量，不保证其它漫画或模型的上下文容量。异常长的 OCR 块只把目标词附近最多 320 字送入 Harness，词典释义提示最多 350 字，译文最多送 600 字；原文/译文被截断的卡自动标为待审，完整原文仍保留在候选和卡片中。

F3/R3 的第二次调用目前使用**同一套所选模型**，不是不同模型的独立交叉验证。档位表示流程和调用量，不宣称准确率按档位递增。翻译服务目前仍按文本调用；不同提供商没有统一的批量接口，同句缓存可减少重复网络请求。实际耗时和费用还取决于用户选择的服务，不在 UI 中伪造固定价格。
每次完成后界面显示实际 Harness 调用次数和耗时；翻译计数是服务调用次数，可能命中缓存，不等于外部计费请求数。

推荐先用**直接筛选＋R0**看完整原文与配图；想减少错义卡时试 R1。若用户愿意做逐卡语境筛选，F2 比 F1 更细；F3/R3 需要对样本评测后才可宣称收益。

## 如何评价档位

在同一部漫画中固定 150–200 个候选，覆盖各 JLPT 等级、未分级、同形异读、拟声词、人名、OCR 错字、口语缩约与只出现一次的词。人工独立标注“值得制卡 / 应排除 / 需复核”，并标正确的原句词位、词义、读音、句译及截图框。

分别报告：筛选 precision、目标词 recall、**错删率**、待审占比；词卡的词形/读音/语境词义/句译/配图各项正确率及整卡全对率；每张被人工接受的卡的模型调用数、实际耗时和费用。先比较 F1/F2/F3 与直接筛选，再比较 R0/R1/R2/R3；评估集不参与调提示词。模型输出自报的“置信度”不能代替人工标注。最终用 Anki 桌面版检查首次导入、再次导入是否保留身份、媒体显示和用户修订更新行为。

## 直接筛选与参考报告的对应

参考 [本机作品的词汇筛选报告](/Users/heyanle/Desktop/project/manga_anki/projects/0001-kyou-wa-kanojo-ga-inaikara/reports/vocabulary-selection-workflow.md)：报告先清洗 OCR 与分词，排除专名、数词、停用词和未知词，再聚合 lemma/读音、书内出现次数与跨页数，结合通用词频和人工例外决定候选，最后人工审核。应用目前使用 Kuromoji 而非报告的 Sudachi B，所以细分词性和未知词判定可能不同；旧候选缺少元数据时保守保留，重新生成候选才能完整应用这些开关。报告里的作品人名、停用词和需排除的 OCR 页属于该作品，不能直接复制到所有书；每书排除词和逐词手动保留承担人工例外。报告中的复合资格条件和“已策展词”需要专门词表，本版提供独立开关与严格预设，并不声称复刻报告最终卡组。

Zipf 参考表在构建期从 `wordfreq 3.1.1` 的日语 large 列表生成，运行时只读取包内 gzip JSON，无需用户 Python。查询候选基本形和已保存的表面形，取可查到的最高值；查不到记为“未知”，不自动当低频。分值 `3 log2(1+出现次数)+log2(1+跨页数)+max(0,2−|Zipf−4.5|)` 只用于“阅读优先度”排序，不用于自动排除。词频数据来源、署名和许可见 [WORDFREQ-ATTRIBUTION.md](../data/WORDFREQ-ATTRIBUTION.md)；上游许可说明见 [wordfreq NOTICE](https://github.com/rspeer/wordfreq/blob/master/NOTICE.md)。

## 当前实现与边界

- `src/core/study/harness.ts` 固定了 Harness 提示、输入 JSON 和结果校验；OCR 文本被明确当作不可信数据。API key 仍留在主进程的 LLM/翻译服务。
- `src/core/study/harness-tool.ts` 定义三种提交 schema；`src/main/study/concurrency.ts` 管每书并发，`src/main/llm/service.ts` 管全应用请求槽与兼容回退。候选和每书工作流在 `study-list.json` 持久化；改动直接规则遇到已有 LLM 检查点时会提示先续跑或明确放弃，避免静默丢失。
- `src/main/study/apkg.ts` 用 `sql.js` 和现有 `fflate` 生成 `collection.anki2`＋媒体；固定 deck/model ID 和每词 GUID。图片名取内容哈希，卡面保留可追溯的原文、书名和页标签。
- 裁图使用 Electron `nativeImage`，目前可靠支持 PNG/JPEG。文字框是 **OCR 块级**，不标称为词的精确像素框；自动裁图和翻译在卡背标记“未经人工校对”。
- 失败或取消不会把未完成输出标成已完成；LLM 请求收到取消信号后中止，按同一输入指纹、档位和配置重试时复用已完成批次。翻译请求最多仍需等待该服务自己的超时。旧 `study-list.json` 可读，旧 TSV 导出仍在。
- 长任务每批发 IPC 事件，窗口折叠时标题仍显示进度；页面重开可读到已落盘的临时判断及上次中断原因。中断后选择“只使用已完成结果”仅改变当前选卡，后续同配置续跑仍会覆盖未处理项。剩余时间是基于已处理项的粗略估计。
- 尚未在 Anki 桌面客户端实际导入，也未在 Windows 上验证新版制卡流程；真实 LLM/翻译供应商的速度、价格和正确率需要上述人工评测。
